# agent_pubsub — multi-channel wire shape

A multi-track publisher modeled after the runtime shape of a real
autonomous computer-use agent — large screenshot frames, a fast
reasoning-token stream, a sparse JSON tool-call stream, and per-
session telemetry datagrams — all on **one QUIC connection**.

> **What is real:** the wire (real QUIC + WebTransport, real PNG
> frames on the screen track, real per-Kind dispatch, real keyframe-
> request handshake, real session-scoped publish-back).
>
> **What is mocked:** the agent itself. Reasoning sentences are
> hardcoded; tool calls cycle through a fixed list. No model runs.
>
> **Where the multistream advantage is *measured**:** in
> [cua](../cua) — not here. This example shows the SHAPE; that
> example prints the numbers.

## Tracks

| Track       | Kind                  | Cadence       | On-wire delivery (per [`feed/pump.go`](../../feed/pump.go)) |
|-------------|-----------------------|---------------|-------------------------------------------------------------|
| `screen`    | `KindVideo`           | 5 Hz, ~30 KB  | stream-per-GOP uni stream                                   |
| `reasoning` | `KindTokens`          | 10 Hz, tiny   | persistent low-latency uni stream                           |
| `actions`   | `KindToolCalls`       | 0.5 Hz, JSON  | fresh bidi stream per AU                                    |
| `telemetry` | datagrams             | 2 Hz, tiny    | unreliable QUIC datagrams (4-byte envelope)                 |

## What this teaches

- `AddTrackSpec` with **distinct `Kind`s** so the per-Kind dispatch in
  [`feed/pump.go`](../../feed/pump.go) picks the right wire pattern
  per modality.
- `SessionHandle.SendDatagram` — fire-and-forget telemetry. Uses the
  4-byte trackId envelope documented in
  [`wire/datagram.go`](../../wire/datagram.go) so a future second
  datagram-kind track wouldn't collide.
- `client.RequestKeyframe(track)` ↔ `Config.OnKeyframeRequest` — the
  loss-recovery handshake. The CLI viewer asks every 10 s and you can
  SEE the server honor it (next `[screen]` line marked `K`).
- `SessionHandle.InboundRecv` — per-session receive of a track the
  *subscriber* published. The browser viewer's click-canvas publishes
  back on `user_actions`; this server drains and logs them, **scoped
  to the originating session** (no `AnySession` mixing under multi-
  subscriber load).
- Real `image/png` on the wire. The SDP advertises `Codec: image/png`
  and the screen track ships actual PNG bytes generated by
  [`examples/internal/synframe`](../internal/synframe/) — the browser
  viewer decodes them and paints real pixels.

## Run (two terminals)

```bash
# Terminal 1 — server
go run ./examples/agent_pubsub/server
# share: https://127.0.0.1:NNNN/wt#slug=...&hash=...

# Terminal 2 — CLI viewer
go run ./examples/agent_pubsub/viewer 'https://127.0.0.1:NNNN/wt#slug=...&hash=...'
```

For the **visual** experience paste the share URL into the browser
viewer: ts-sdk/examples/viewer.

The interleaving across `[screen]` / `[reasoning]` / `[action]` /
`[telemetry]` rows IS the visual — four QUIC streams + datagrams
making progress concurrently on one connection.

## What this does NOT prove

- That the per-Kind dispatch is **measurably** faster than a naive
  single-track shape. That's [cua](../cua)'s job — it prints actual
  p50/p95/max numbers comparing naive vs multistream dispatch on the
  same workload.
